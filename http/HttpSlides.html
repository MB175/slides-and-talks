HTTP Basics

Hypertext Transfer Protocol — the foundation of data communication on the Web

What is HTTP?

Definition

HTTP (Hypertext Transfer Protocol) is an application-layer protocol for transmitting hypermedia documents. It follows a client-server model where the client sends a request and the server returns a response.

It is stateless — each request is independent and carries all context needed.

Key Properties

📡 Text-based (HTTP/1.x) or binary (HTTP/2+)

🔄 Request → Response cycle

📦 Stateless — no memory between requests

🔌 Runs over TCP (or QUIC for HTTP/3)

🔒 HTTPS = HTTP + TLS encryption

📋 Defined in RFC 9110 (HTTP semantics)

The Request/Response Cycle

Client
Browser / curl
→
HTTP Request HTTP Response
←
Server
nginx / Go / …

1. Client Sends Request

Method + URL + Headers + optional Body

2. Server Processes

Routes, authenticates, reads/writes data

3. Server Returns Response

Status code + Headers + optional Body

HTTP Methods

Safe, idempotent, cacheable — know the semantics

Methods & Their Properties

Method Purpose Safe Idempotent Cacheable Typical Use
GETRetrieve a resource✅ Yes✅ Yes✅ YesRead web pages, API data
HEADHeaders only, no body✅ Yes✅ Yes✅ YesCheck if resource exists/changed
POSTCreate / submit data❌ No❌ No🔶 SometimesForms, create records
PUTReplace entire resource❌ No✅ Yes❌ NoFull update
PATCHPartial modification❌ No🔶 Usually❌ NoPartial update
DELETERemove a resource❌ No✅ Yes❌ NoDelete records
OPTIONSDiscover capabilities✅ Yes✅ Yes❌ NoCORS preflight
TRACELoop-back diagnostic✅ Yes✅ Yes❌ NoDebug proxy chains
CONNECTEstablish TCP tunnel❌ No❌ No❌ NoHTTPS through proxies

Reference: RFC 9110 — HTTP Semantics. TRACE is often disabled for security (cross-site tracing). CONNECT is used by HTTP proxies to tunnel TLS traffic.

Method Semantics Explained

Safe

A method is safe if it does not modify server state. GET and HEAD are safe — calling them has no side effects.

Safe methods can be prefetched, cached, and retried freely.

Idempotent

A method is idempotent if calling it N times produces the same result as calling it once. PUT and DELETE are idempotent.

POST is NOT idempotent — each call may create a new resource.

Cacheable

A method is cacheable if its response can be stored for future reuse. Only GET and HEAD are cacheable by default.

POST responses can be cached if explicit Cache-Control is set.

Content Negotiation

How It Works

The client tells the server which formats, languages, and encodings it accepts. The server picks the best match.

GET /api/users/42 HTTP/1.1
Accept: application/xml;q=0.9, application/json;q=1.0
Accept-Language: de-DE, en;q=0.8
Accept-Encoding: br, gzip;q=0.8

q = quality factor (0–1). Higher = more preferred. Default is 1.0.

Server Responses

✅ Match found

HTTP/1.1 200 OK
Content-Type: application/json
Content-Language: de-DE
Vary: Accept, Accept-Language

Vary tells caches: this response depends on these request headers.

❌ No match

HTTP/1.1 406 Not Acceptable
Content-Type: application/json

{"error":"Server cannot produce
  application/xml or application/json"}

Status Codes

Understanding every class of HTTP response status

Status Code Classes

1xx Informational

Interim response. The request was received, processing continues.

100 Continue · 101 Switching Protocols · 103 Early Hints

2xx Success

The request was successfully received, understood, and accepted.

200 OK · 201 Created · 204 No Content · 206 Partial Content

3xx Redirection

Further action needed to complete the request.

301 Moved Permanently · 302 Found · 304 Not Modified · 307 Temporary Redirect

4xx Client Error

The request contains bad syntax or cannot be fulfilled.

400 Bad Request · 401 Unauthorized · 403 Forbidden · 404 Not Found · 405 Method Not Allowed · 409 Conflict · 429 Too Many Requests

5xx Server Error

The server failed to fulfill a valid request.

500 Internal Server Error · 502 Bad Gateway · 503 Service Unavailable · 504 Gateway Timeout

Important Status Codes in Detail

200 OK

Standard success response. Body contains the requested resource or result.

201 Created

New resource was created. Typically returned by POST. Location header points to the new resource.

204 No Content

Success, but no response body. Common for DELETE or PUT where no data needs returning.

301 Moved Permanently

Resource has moved forever. Clients and search engines update the URL. Location header has the new URL.

304 Not Modified

Cache validation success. Client's cached version is still fresh — no body transferred, saving bandwidth.

206 Partial Content

Only part of the resource returned (Range request). Used for resumable downloads and video streaming.

Redirect Codes — 301 vs 302 vs 307 vs 308

CodeNamePermanent?Method Change?When to Use
301Moved Permanently ✅ Yes ⚠️ May change POST→GET Permanent URL change (SEO-friendly)
302Found ❌ No ⚠️ May change POST→GET Temporary redirect (legacy)
307Temporary Redirect ❌ No ✅ Method preserved Temporary redirect — keeps POST as POST
308Permanent Redirect ✅ Yes ✅ Method preserved Permanent URL change — keeps POST as POST

The Method-Change Trap

With 301 and 302, browsers historically changed POST to GET on redirect — even though the spec says they shouldn't.

Fix: Use 307/308 when you need the HTTP method to stay the same (e.g. redirecting a POST to a new API endpoint).

Quick Rule

Permanent + safe to change method? → 301

Permanent + keep method? → 308

Temporary + safe to change method? → 302

Temporary + keep method? → 307

How It Works

Servers enforce rate limits to prevent abuse. When exceeded, they respond with 429.

CORS — Cross-Origin Resource Sharing

What is CORS?

Browsers block JavaScript from making requests to a different origin (domain, protocol, or port) by default. CORS headers let servers opt in to cross-origin access.

3️⃣ If allowed, browser sends the actual request

How JWT Works

1. User logs in with credentials

2. Server creates a signed JWT and returns it

3. Client stores it (localStorage, cookie)

4. Client sends Authorization: Bearer <jwt> on each request

5. Server verifies signature — no session storage needed

⚠️ JWT is not encrypted by default — anyone can decode the payload. Only the signature ensures integrity.

HPACK & Huffman

Header compression in HTTP/2 — how it really works

HPACK — Header Compression

Three Compression Techniques

1. Static Table — 61 pre-defined common headers (e.g., :method: GET = index 2). Referenced by index number.

2. Dynamic Table — Connection-specific table that grows as new headers are seen. Both sides maintain identical copies.

3. Huffman Coding — Compresses header string values using frequency-based variable-length encoding.

Why It Matters

HTTP/1.1 sends headers as plain text on every request — often 500+ bytes of repetitive data.

With HPACK, common headers like :method: GET compress to a single byte (index reference).

Typical savings:

First request: ~30% smaller headers

Subsequent requests: ~85% smaller (dynamic table hits)

Huffman Coding — Interactive Example

The Concept

Frequent characters get short codes, rare characters get long codes. This is optimal prefix-free encoding.

CharacterFrequencyHuffman Code
Avery high0
Bhigh10
Clow110
Dvery low111

Encoding Example

Input string: A A A B C A D

Encoded: 0 0 0 10 110 0 111

= 0001011001111

🧠 Without Huffman: 7 chars × 8 bits = 56 bits

🧠 With Huffman: 13 bits — that's a 77% reduction!

⚠️ HPACK uses a fixed Huffman table (RFC 7541, Appendix B) — not dynamically built per connection. The table is optimized for typical HTTP header values.

HTTP/3 & QUIC

Why HTTP/3?

HTTP/2's biggest problem: TCP head-of-line blocking. If one packet is lost, ALL streams on that TCP connection stall.

HTTP/3 moves to QUIC (built on UDP), where each stream is independently loss-recovered.

Key Benefits

🚀 0-RTT connection setup — resuming previous connections needs zero round-trips

📦 Independent streams — packet loss on one stream doesn't block others

🔒 Built-in TLS 1.3 — encryption is mandatory and integrated

🔄 Connection migration — connections survive IP changes (WiFi → cellular)

📊 QPACK header compression (evolved from HPACK)

HTTP Upgrade — Protocol Negotiation

ALPN (TLS-based, HTTP/2)

Part of the TLS handshake. Client and server negotiate the application protocol.

ClientHello:
  ALPN extension: h2, http/1.1

ServerHello:
  ALPN extension: h2

→ HTTP/2 connection established!

ALPN = Application-Layer Protocol Negotiation (RFC 7301)

Upgrade Header (h2c, cleartext)

For unencrypted HTTP/2, the client can request an upgrade via HTTP/1.1:

GET / HTTP/1.1
Host: example.com
Upgrade: h2c
HTTP2-Settings: <base64>
Connection: Upgrade, HTTP2-Settings

h2c = HTTP/2 cleartext. Rarely used in production — most HTTP/2 uses TLS.

WebSockets start as an HTTP request with an Upgrade header. Once upgraded, the connection becomes full-duplex bidirectional.

      
// Client request
GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: x3JJHMbDL1EzLkh9GBhXDw==
Sec-WebSocket-Version: 13

// Server response
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: HSmrc0sMlYUkAGmm5OPpG2HaGWk=

    

    

      
WebSocket vs HTTP

      

        
HTTPWebSocket

        
          
DirectionRequest → ResponseBidirectional

          
ConnectionShort-lived (per request)Persistent

          
OverheadHeaders on every requestMinimal framing

          
Use casesREST APIs, web pagesChat, live updates, gaming

        
      

    

  






  
Security Headers

  

    

      
Essential Security Headers

      

        
HeaderPurpose

        
          
Strict-Transport-SecurityForce HTTPS for all future requests (HSTS)

          
Content-Security-PolicyControl which resources the browser can load (XSS protection)

          
X-Frame-OptionsPrevent clickjacking by blocking iframe embedding

          
X-Content-Type-OptionsPrevent MIME type sniffing (nosniff)

          
Referrer-PolicyControl how much referrer info is shared

          
Permissions-PolicyRestrict browser features (camera, mic, geolocation)

        
      

    

    

      
Example: Secure Response

      
HTTP/1.1 200 OK
Strict-Transport-Security:
  max-age=31536000; includeSubDomains
Content-Security-Policy:
  default-src 'self';
  script-src 'self' cdn.example.com
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin
Permissions-Policy:
  camera=(), microphone=()

Server-Sent Events (SSE)

  

    

      
How SSE Works

      
A long-lived HTTP connection where the server pushes events to the client. Uses standard HTTP — no protocol upgrade needed.

      
GET /events HTTP/1.1
Accept: text/event-stream

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

data: {"user":"Ada","action":"login"}

event: notification
data: {"msg":"New message from Alan"}

id: 42
data: {"heartbeat":true}

    

    

      
SSE vs WebSocket vs Long Polling

      

        
SSEWebSocketLong Polling

        
          
DirectionServer → ClientBidirectionalServer → Client

          
ProtocolHTTPWS (upgrade)HTTP

          
ReconnectBuilt-inManualManual

          
Binary data❌ Text only✅ YesYes (base64)

          
ComplexityLowMediumHigh

          
Use caseFeeds, notifications, dashboardsChat, gaming, collaborationLegacy fallback

        
      

      
SSE is often the simplest choice for one-way server push. Browser API: new EventSource('/events')
